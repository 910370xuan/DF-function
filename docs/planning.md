# 華暉 LINE 訂單自動化：架構規劃與待確認事項

依據：《華暉 LINE 訂單自動化需求規格書 v1.0》（2026-11-09）
目標：提高出貨作業效率，盡量用**免費額度**完成。

---

## 0. 先講結論

1. **量很小**（每天約 50 則訊息、約 5 筆訂單）。所有雲端服務都能落在免費額度內，**真正的成本風險只有 LINE 推播額度**和**AI 免費方案的資料使用條款**。
2. **最省時間的是「10:00 自動產出、自動列印出貨單和標籤」**，不是 AI 辨識。建議第一階段先把產單和列印做到穩定，AI 辨識再逐步加上去。
3. **辨識以規則為主，AI 為輔**：先做「LINE 帳號 → 店家」綁定和「商品別名字典」，大部分訂單用程式就能確定，只有剩下的才送 AI。這樣更省錢，也更不會亂猜。
4. **Excel 產單建議放在辦公室電腦**（Windows + 正版 Excel），不放雲端：版型、字型、公式 100% 一致，還能直接送到印表機。雲端（GitHub Actions + LibreOffice）只當備援。
5. **管理員通知盡量用「回覆」而不是「推播」**：LINE 的 reply 免費、push 要算額度。

## 1. 建議架構（全免費版）

```
客戶 ──LINE 1:1──▶ LINE 官方帳號（聊天模式 + Webhook 同時開啟）
                          │ Webhook（含簽章）
                          ▼
              Cloudflare Workers（免費方案）
              ├─ 驗證簽章、事件 ID 去重
              ├─ 原始事件寫入 D1
              ├─ 每 5 分鐘 Cron：合併「安靜超過 N 分鐘」的對話 → 解析
              │     1) 帳號→店家綁定表（確定性）
              │     2) 商品別名字典 + 數量規則（確定性）
              │     3) 剩下不確定的才呼叫 AI（只做抽取 + 風險標記）
              ├─ 金額／10+1／折抵／訂單編號：程式計算
              ├─ 異常 → 管理群卡片（postback 冪等處理）
              └─ 10:00 Cron：凍結批次 → 產生批次資料（JSON）
                          │
          ┌───────────────┴────────────────┐
          ▼                                ▼
 辦公室電腦（主要）                  GitHub Actions（備援）
 Python + Excel(COM)                 openpyxl + LibreOffice
 填入原始 .xlsx 模板                 輸出 Excel / PDF
 匯出 PDF、直接列印                  （字型可能有差異）
          │                                │
          └──────────▶ 回報「已產單／已列印」◀┘
                          │
                          ▼
              Google Sheets（廠商、商品別名、價格 主檔維護 & 每日檢視）
              Cloudflare R2（保存每日 Excel/PDF 版本，10GB 免費）
```

### 各元件免費額度（需上線前再次核對官方最新資訊）

| 元件 | 用途 | 免費額度（約） | 本案用量 | 風險 |

## 2. 關鍵流程設計

### 2.1 客戶識別（最重要的效率點）
- 建立「LINE userId → 店家/分店」綁定表。第一次遇到新帳號時發一張卡片給管理員：「這是哪一家店？」選一次之後就自動判斷。
- 同一個帳號負責多間分店時，標記為「多店帳號」，訊息裡沒寫分店才算異常。
- 效果：客戶辨識幾乎不用 AI，也不用猜。

### 2.2 多則訊息合併
- 同一位客戶的訊息先暫存，**最後一則之後安靜 N 分鐘（建議 10–15 分鐘）**才合併解析。
- 09:55 起強制把所有暫存的對話解析完，確保 10:00 批次完整。
- 已解析之後又來新訊息 → 視為「修改／追加」，跟原訂單比對，有衝突才通知管理員。

### 2.3 規則優先、AI 補位
1. 商品別名字典（例：「小電池」「直流」「電力盒 4pin」→ 標準品號），由管理員在 Google Sheet 維護。
2. 正規表達式抓「品項 + 數量」。
3. 規則能完整解析且無衝突 → 直接入列。
4. 規則解析不完整 → 送 AI，要求輸出固定 JSON（品項、數量、日期、信心、疑點），**AI 輸出仍要通過字典與規則驗證**，沒通過就當異常。
5. 每筆都保留「原始訊息 → 解析結果」對照，方便日後補字典、降低 AI 使用量。

### 2.4 管理員卡片的防重複
- 卡片按鈕使用 postback，資料裡帶 `訂單ID + 版本號`。
- D1 用條件更新：`UPDATE ... WHERE id=? AND version=? AND status='待確認'`，只有第一個成功的人生效。
- 其他人按舊卡片 → 用 **reply（免費）** 回「已由 OOO 於 10:03 處理」。

### 2.5 管理員在後台手動回覆的問題
Webhook 讀不到管理員在 OA 後台打的字，建議用以下其中一種（由輕到重）：
- **A. 管理群快速指令（推薦）**：在內部管理群輸入 `#出貨 店名 明天` 或 `#出貨 店名 11/12`，Bot 解析後用 reply 確認。群組訊息進 Webhook 是免費的。
- **B. 卡片補記**：系統若偵測到「客戶有訊息但沒成單」，09:30 彙整一次清單，讓管理員在卡片上點選日期。
- **C. LIFF 小表單**：在管理群放一個連結，開啟簡單表單選店家、品項、日期（也是免費）。

### 2.6 10:00 批次
1. Worker Cron（台灣 10:00 = UTC 02:00）凍結批次：前一天及更早未出貨 + 今天 10:00 前收到且應今天出貨的訂單。
2. 產生批次 JSON（店家、品項、數量、單價、優惠、編號）存 D1/R2。
3. 辦公室電腦上的程式每分鐘輪詢（或 10:00 排程）抓批次 → 填入 Excel 模板 → 匯出 PDF → 送印表機 → 回報狀態。
4. 同時以 Actions 備援：如果 10:15 還沒收到辦公室電腦回報，就觸發 GitHub Actions 產 PDF 並上傳 R2，通知管理員。
5. 補單批次：編號 `日期-02`、`日期-03`…，不覆寫已列印的檔案。

### 2.7 箱外標籤 3 格排版
- 依批次店家數量每 3 家一頁（8 家 = 3+3+2）。
- 用辦公室 Excel 列印可保證跟現在貼紙對齊；第一次要用實體貼紙試印校準。

## 3. LINE 推播額度：最需要優化的地方

推播到群組時，**群組裡每一位成員都算一則**。若管理群有 3 位管理員：

| 通知 | 次數/月（以 22 個工作天估算） | 消耗 |
|---|---|---|
| 每日批次摘要 1 則 | 22 | 66 |
| 異常卡片平均每天 2 則 | 44 | 132 |
| 合計 | | **≈ 198 / 200** |

已經很接近上限，而且**官方帳號的群發廣播也共用同一個額度**。優化方法：

1. **能用 reply 就用 reply**：管理員按卡片、輸入指令時，Bot 的回覆都免費。
2. **異常合併發送**：不要一筆一張卡，改成每 30–60 分鐘彙整一張（Carousel 一則可以放多張卡）。緊急的才即時發送。
3. **改成「拉」**：09:30 推一則「今天有 N 筆待確認」，管理員輸入 `#待確認` 才用 reply 列出明細。
4. **每日摘要可改為一個有權限控管的網頁連結**（Cloudflare Pages + Cloudflare Access，50 人內免費）。
5. 如果還不夠：通知改用 Telegram Bot 或 Email（免費），LINE 只用來收訂單。
6. 系統內建「本月 push 用量」計數，到 80% 自動改為合併模式。

## 4. AI 選擇

| 選項 | 費用 | 中文效果 | 注意 |
|---|---|---|---|
| Google Gemini API 免費層 | 免費（有速率限制） | 好 | 免費層的輸入資料可能被用來改善產品，客戶訊息有個資疑慮，需去識別化或經公司同意 |
| Cloudflare Workers AI | 每日免費額度 | 中等 | 跟 Worker 同平台，整合最簡單 |
| 付費 API（Claude、Gemini 付費等） | 以本案用量估計每月約數美元等級 | 好 | 資料不用於訓練；需信用卡 |

建議：**先用規則 + Gemini 免費層（送出前把電話、地址遮掉）開發測試**，量測實際的命中率和 token 數之後，再決定正式上線要不要換成付費方案。系統把 AI 呼叫包成一個介面，換供應商只改一個設定。

## 5. 對需求規格的優化建議

1. **分階段交付**（降低風險、早點有效益）
   - **P0（約 1 週）資料準備**：拿到 Excel、對話樣本、主檔；確認 LINE 方案與額度。
   - **P1 產單自動化**：Webhook 收訊息 + 帳號綁定 + 管理員在 Google Sheet 確認訂單 → 10:00 自動產出 Excel/PDF/標籤並列印。**光這一步就能省掉打單、排版、清空工作表的時間。**
   - **P2 自動辨識**：規則 + AI 解析、異常卡片、補單批次。
   - **P3 進階**：回收折抵、庫存扣帳、出貨確認、客戶自動回覆確認。
2. **增加「影子模式」**：P2 上線前先跑 1–2 週，系統只產生建議、不產單，管理員對照人工結果，量測正確率再正式切換。
3. **多一種狀態：「已收到未成單」**，避免客戶只說「老樣子」或只傳貼圖時被忽略。
4. **「老樣子／同上次」**：可以直接帶出上一張訂單當草稿，但一定要列為異常讓管理員確認。
5. **圖片／語音訊息**：先確認客戶會不會傳手寫單照片或語音。如果會，P2 再用 AI 看圖；P1 一律列為異常。
6. **訂單編號**：由 D1 依「年月 + 流水號」用交易方式產生，避免兩批次撞號；跨年規則請公司確認。
7. **假日與「下週一」**：建一張「出貨日曆」表（Google Sheet），國定假日和公司休假由管理員維護，程式依日曆計算。
8. **備份**：D1 每日匯出到 R2；Google Sheet 本身有版本紀錄。
9. **測試**：把實際（去識別化）對話存成測試案例，每次修改規則都自動重跑，避免改 A 壞 B。

## 6. 開工前需要提供的資訊

**必要（沒有就無法開始）**
1. 「華暉-115年庫存管理及出貨單.xlsx」原始檔，最好附一份填好的出貨單和貨運單範例。
2. 30–50 段去識別化的真實訂單對話（包含修改、模糊品名、多則訊息、圖片、補單等情況），以及每段對話「正確應該產出的訂單」。
3. 廠商主檔：店名、分店、地址、電話、對應的 LINE 名稱。
4. 商品清單：品號、正式名稱、常見別名、單價、10+1 規則、4pin/8pin 規則。
5. LINE 官方帳號目前的方案、每月群發／推播用量；是否允許官方帳號加入內部群組。

**重要（影響設計）**
6. 辦公室電腦：作業系統、是否有 Excel、10:00 是否開機、印表機與標籤紙型號（紙張尺寸、三格位置）。
7. 訂單編號規則（跨月／跨年）、假日出貨規則、「下週一」遇假日怎麼算。
8. 回收電力盒折抵的金額、驗收流程、核銷方式（可以先排到 P3）。
9. 「已出貨」如何確認（點卡片？掃描？順豐單號回填？）。
10. 公司是否同意客戶訊息送到外部 AI 服務；若不同意，P2 只能用規則或改用付費且不訓練的方案。
11. 各雲端帳號（Cloudflare、Google、GitHub、LINE Developers）用公司帳號申請，並決定由誰保管。

## 7. 主要風險

| 風險 | 影響 | 對策 |
|---|---|---|
| LINE push 額度用完 | 通知中斷 | reply 優先、合併、改用拉取、用量監控、備援通知管道 |
| 辦公室電腦 10:00 沒開機 | 未自動列印 | GitHub Actions 備援產 PDF + 通知 |
| LibreOffice 字型或版面差異 | 雲端 PDF 跑版 | 主要用 Excel；雲端只當備援並安裝相近字型 |
| AI 誤判 | 錯單 | 規則驗證、信心不足即列異常、影子模式 |
| 管理員後台口頭承諾沒被記錄 | 漏出貨 | 管理群指令、09:30 未成單清單 |
| 免費方案條款變更 | 突然要付費 | 元件可替換、保留付費方案估價 |
